## Executive summary

The firmware was already bench-hardened (wrap-safe timing, bounded serial
discipline, binary-safe multipart payloads, honest failure reporting). This
audit found one CRITICAL wiring-of-software bug — the station's documented
serial commands were unreachable — plus a set of runtime-reliability gaps
where the "self-healing" claims only covered boot-time failures, and the
card-first auto-capture work-in-progress needed its contracts enforced.

## What changed (verified: native 96/96 · `pio run` esp32dev + esp32cam SUCCESS)

| Area | Change | Why |
|---|---|---|
| **Serial dispatch (CRITICAL)** | command grammar (ENTER/`a`/`e`/`c`) is tried FIRST via `TerminalCaptureTrigger::feedLine()`; only unrecognized lines go to the password console | `a <uid>` / `e <id>` / `c` were consumed as wrong-password attempts, poisoned the lockout, and never ran |
| Auto-capture contract | classify upload failure KEEPS the armed event (BUTTON/ENTER retryable, 90 s bound); re-tap of the same event no longer re-arms; `e 0` / oversized ids rejected bilingually | the arm was consumed on failures, contradicting `station.h` |
| Associate 404 semantics | only `no_pending_capture` / `already_associated` clear the pending capture; card rejections keep it | a mistyped `a <uid>` used to orphan the student's photo |
| Camera self-heal | 3 consecutive `fb_get` failures flip `cameraOk_` → existing re-init cadence engages (`CAMERA_FAILURES_BEFORE_REINIT`) | runtime death was never detected after a healthy boot |
| RC522 self-heal | periodic VersionReg probe (every 5 s while healthy) can revoke `healthy_` | a reader that died mid-day stayed "healthy" forever, taps silently dead |
| Memory | capture buffer falls back to DRAM when PSRAM allocation fails | PSRAM-less boards booted but could never capture |
| Wrap safety | buzzer chirp uses elapsed-style compare (`BUZZER_CHIRP_MS`) | the last absolute-deadline compare broke at the 49.7-day wrap |
| Parsing | `extractLongField` tolerates whitespace; no `isdigit(char)` UB | backend reformatting must not kill the associate flow |
| Boot honesty | placeholder warning also flags `API_BASE_URL = localhost/127.0.0.1`; templates ship a LAN placeholder | fresh checkouts passed the warning then failed every request |
| Hygiene | dead `Mode::callType()` / `modeKindToString()` removed; banner lines completed EN+ES; `secrets.camera.h.example` no longer claims "no mode console"; command/password collision note added | docs and dead code must not mislead |
| Docs | HARDWARE_SETUP (EN/ES) now shows the READER pin map (SCK 18 / MISO 19 / MOSI 23 / SS 5 / RST 27) — it had presented the STATION's pins as reader defaults; library names/versions corrected (`bblanchon/ArduinoJson ^7.4.3`, `miguelbalboa/MFRC522 ^1.4.11`); test counts corrected to 96 everywhere | an operator wiring from the old table would build a dead reader |

## Remaining recommendations

1. The serial line handling for long operations: during the ~10 s classify
   upload the loop is blocked (documented); typing (not pasting) commands is
   fine, but a paste burst mid-upload can overflow the RX buffer — a
   drain-Serial-into-LineBuffer step around long uploads would close it.
2. Add a MANUAL_VERIFICATION_CHECKLIST section for the card-first
   auto-capture flow before the next bench session (the flow's docs and
   tests are now consistent; the checklist doesn't yet name it).
3. `extractLongField` is the last non-ArduinoJson parse in the firmware;
   migrating it into a host-testable PresenceCore helper would close the
   final drift surface (already partially hardened in place).
4. The mode password compares non-constant-time and transport is plain
   HTTP — both deliberate for the school-LAN bench scope (ADR-005); revisit
   if the console is ever exposed beyond USB serial or traffic leaves the LAN.
