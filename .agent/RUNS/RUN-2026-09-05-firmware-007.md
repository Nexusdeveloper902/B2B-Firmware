## Root cause (verified against source, not guessed)

- The two `/api/v1/admin/cards/pair` POSTs appear in the backend's
  `php artisan serve` log at the tap timestamps → the device DID reach
  Laravel; both were rejected by `ResolveReaderToken`.
- `ResolveReaderToken` (B2B-Core) 401s on `empty(bearerToken())` OR on
  no `readers.api_key` match. Laravel's `bearerToken()` only reads the
  literal `Bearer ` scheme.
- arduino-esp32 HTTPClient source (framework 3.20017, local pio cache):
  `setAuthorization(const char*)` → `_base64Authorization`, and the
  request builder emits `Authorization: <_authorizationType> <value>`
  with `_authorizationType = "Basic"` BY DEFAULT.
- Therefore EspApiClient sent `Authorization: Basic <READER_API_KEY>`
  since TASK-001 → EVERY real-hardware call 401'd regardless of key
  validity. The device had never successfully authenticated.
- Why nothing caught it: docs' curl examples write the header manually;
  backend tests forge requests; native tests mock the ApiClient; the
  owner's TASK-005 curl "proof" exercised curl, not the device.
- Honesty correction recorded: SNAPSHOT-006's "Reader key: PROVEN
  WORKING (TASK-005 evidence)" overstated — it proved the backend row,
  not the device transport.
