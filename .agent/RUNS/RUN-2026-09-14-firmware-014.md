## Addendum — bench found the real blocker (same day)

- Symptom: phone taps showed `SAK=0x20 ATS=0B` + ever-changing `08…`
  UIDs; RATS retries + max RxGain did not move it.
- Root cause (vendored driver, proven by reading its source): MFRC522
  1.4.12 `PICC_Select` parses a good ATS into a stack-local `Ats` and
  never assigns `tag.ats` — `tag.ats.size` is permanently 0, so every
  `ats.size > 0` gate (ours AND the standalone prototype's) is dead
  code with this library version. RATS was almost certainly succeeding;
  the bytes were discarded. The prototype's HCE end-to-end likely never
  ran against 1.4.12 — this bench is its first real activation.
- Fix (`Rc522NfcReader::adoptAts`): direct `PICC_RequestATS` on the
  selected target (legal retransmission) + adopt into `tag.ats`
  (size/tc1/blockNumber) with the real status logged; up to 3 WUPA +
  reselect + adopt rounds; no PPS (106 kbit/s suffices). MIFARE path
  untouched. All three envs SUCCESS, native still 111/111.

## Addendum 5 — park-and-activate restructure (same day)

- Decisive log reading: post-HaltA the A56 answers nothing (RATS /
  WUPA / REQA) until field re-entry — so the driver's discovery select
  (immediate RATS + HaltA-on-timeout) poisoned every tap, and all four
  prior retry designs were aimed at corpses. Settle-sweeps could never
  work: any RATS after the first timeout is dead by construction.
- Restructure (`Rc522NfcReader::poll`): discovery via qualified BASE
  Select (no RATS, no surprise HaltA — identical frames for MIFARE);
  ISO-DEP sighting parks the untouched selected session 400 ms in
  radio silence; then the tap's FIRST RATS fires via adoptAts. WUPA
  retry loop deleted (measured dead). MIFARE branch now reads tag.uid
  (same bytes, new source — needs one bench card tap to re-confirm).
- All envs SUCCESS, native 111/111. If settled first-RATS still times
  out, the controller genuinely won't talk and we go model-specific.

## Addendum 8 — mutual-timeout race (same day, owner-observed)

- Owner: exactly ONE "select aid" per tap in the app log, and app
  events only render with the app in focus. Combined with reader-side
  SELECT x3 timeouts, the diagnosis is a MUTUAL timeout race: our RX
  window (~10 ms driver loop) vs the warm-app answer path (several ms
  via controller→DH→app→DH→controller), PLUS the phone's own
  frame-wait timer tearing the session down when our next block is
  200 ms late — which is why retries arrived at a dead session and the
  app logged only attempt 1. Focus matters doubly: foreground =
  process priority (fast answers) + the event listener only renders
  while resumed (display mechanics, by design).
- Fix in this flash: TIGHT retries (SELECT 10x15 ms, CHALLENGE 6x25 ms)
  = continuous RX coverage for slow answers + session keepalive (each
  arrival resets the phone's timer). Safe: block number toggles only
  on success (vendored source), SELECT idempotent app-side.
