## Root-cause analysis (why the user read "not working")

- The 404 is CORRECT backend behavior and proves the key check PASSED:
  B2B-Core `ResolveReaderToken` runs before the tap handler and returns
  `401` when no `readers` row matches the Bearer key; `404 Card not
  recognized` is only produced AFTER the reader identity was accepted
  (`TapService::registerTap`: no `cards` row for that UID). So the
  user's key is fine — the failure was in the doc example.
- TASK-004's verification snippet carried `-d '{"credential_uid":
  "A-SEEDED-UID"}'` — a placeholder that reads as a real seeded value.
  A user following the doc verbatim (as this one did) expects a `200`
  and reads the `404` as breakage.
- Compounding gap: the docs showed only the READERS table from the
  `./run setup` output. The CARDS table — printed immediately above it,
  the only place the real seeded `credential_uid`s live — was never
  shown or referenced. DemoSeeder mints a random 12-char uppercase UID
  per student (firstOrCreate → stable across re-runs) and prints both
  tables every seed run.
- Conclusion: documentation defect, not a protocol/code defect. Same
  class as TASK-004 (operator experience), narrower scope.

  post-clone secret scan — full 32-char reader key in the task-file

  discipline stands: transcripts in records get placeholders, never
  key bytes. Rotation path if wanted: update `readers.api_key`
  server-side (PAIRING.md Option B).

- A doc example that LOOKS like a real value will be executed verbatim
  by a careful user: placeholders must be unmistakable placeholders,
  and any "verify with X" instruction must say where a real X comes
  from — verified end-to-end this run (the user's transcript IS the
  repro).
- Cross-repo evidence chain matters for triage: the 401→404 transition
  in the user's two transcripts was itself the diagnostic (middleware
  accepted the key this time), no hardware access needed.
